# Security Decisions

This document records selected security and architecture decisions that materially changed NautilusBook during development.

## SD-01 — The LLM is not a database agent

**Decision:** the model produces a constrained structured plan. Domain services decide what can be persisted.

**Why:** language models are probabilistic. An incorrect interpretation must not bypass authorization, state invariants, or catalog resolution.

**Consequence:** there is more deterministic code after inference, but the application remains testable even when the model behaves imperfectly.

---

## SD-02 — Webhook acknowledgment is separated from message processing

**Decision:** persist the incoming event and acknowledge WAHA quickly; perform LLM inference in a worker.

**Why:** model inference can take seconds or experience cold starts. Holding a webhook open couples model latency to retry behavior.

**Consequence:** the system needs an inbox state machine, worker and retry/dead-letter behavior.

---

## SD-03 — Duplicate external events must be safe

**Decision:** external WhatsApp message IDs participate in idempotent processing.

**Why:** retries are normal network behavior. Correctness cannot assume exactly-once delivery.

**Consequence:** re-delivery can be acknowledged without repeating a journal mutation.

---

## SD-04 — WhatsApp identity is not equivalent to a phone number

**Decision:** keep opaque WhatsApp identity (`@lid`) separate from a resolved phone number.

**Why:** treating an opaque identity as a phone number caused incorrect authorization and persistence behavior during real testing.

**Consequence:** account linking can use the stable messaging identity while phone resolution remains optional.

---

## SD-05 — Ambiguity fails closed

**Decision:** if multiple books are plausible and there is no unique active reference, ask for clarification instead of guessing.

**Why:** a false positive can mutate durable user data.

**Consequence:** some conversations require an extra clarification message, which is preferable to silent corruption.

---

## SD-06 — Browser sessions use revocable server-side session state

**Decision:** access tokens are linked to persisted authentication sessions; refresh tokens rotate and can be revoked.

**Why:** a standalone long-lived JWT makes logout/revocation difficult and refresh-token theft harder to contain.

**Consequence:** authentication includes session storage and token lifecycle management.

---

## SD-07 — User uploads are reprocessed, not merely stored

**Decision:** decode, validate and re-encode accepted cover images.

**Why:** filename extensions and user-provided MIME types are not trustworthy; image metadata may also reveal unnecessary information.

**Consequence:** uploaded covers become controlled WebP assets rather than arbitrary original files.

---

## SD-08 — Personalized covers belong to a reading/user context

**Decision:** a user’s uploaded cover is not written to a globally shared catalog record.

**Why:** one user should not be able to change the visual representation of a book for every other user.

---

## SD-09 — Self-hosted storage is a first-class deployment option

**Decision:** media storage uses an abstraction with local/self-hosted filesystem as the default backend.

**Why:** the product should not require paid object storage to operate.

**Consequence:** operational responsibilities such as backup, permissions and disk monitoring become explicit.

---

## SD-10 — Public portfolio and private product are separate repositories

**Decision:** publish engineering documentation, architecture and security lessons separately from the commercial source code.

**Why:** portfolio value does not require giving away the private product implementation or historical secrets.

**Consequence:** public documentation must be maintained intentionally and should never be generated by copying the private repository wholesale.
